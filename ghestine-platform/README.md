# دیجی بال پی | بستهٔ شمارهٔ ۳

این شاخه برای مرتب‌سازی و تکمیل فایل‌های بستهٔ شمارهٔ ۳ پروژهٔ واقعی دیجی بال پی آماده شده است.

## فایل‌ها و مسیرها

- آرشیو ورودی دست‌نخورده: `ghestine-platform/ghestine-all3.zip`
- سورس استخراج‌شده و قابل بازبینی: `ghestine-platform/source/all3/`
- صفحهٔ اصلی: `source/all3/web/template-v3.html`
- ورود: `source/all3/web/login.html`
- ثبت‌نام و تأیید کد: `source/all3/web/register.html`
- حساب مشتری: `source/all3/web/profile.html`
- درگاه مدیریت با بررسی نقش: `source/all3/web/admin.html`

## تغییرات این مرحله

- مسیرهای ورود، ثبت‌نام، حساب مشتری و درگاه مدیریت که صفحهٔ اصلی به آن‌ها لینک می‌دهد، در سورس اضافه شدند.
- صفحات ورود و ثبت‌نام از قرارداد واقعی ماژول امنیت بسته استفاده می‌کنند: کپچا، درخواست OTP، تأیید OTP، ورود با رمز و ثبت‌نام با تیکت تأیید موبایل. حالت شبیه‌سازی خاموش است؛ در صورت خطای API، صفحه خطا نشان می‌دهد و نشست یا نتیجهٔ ساختگی ایجاد نمی‌کند.
- صفحهٔ حساب، اطلاعات را از `/api/v1/Auth/me` می‌خواند و در صورت 401/403 به ورود برمی‌گردد.
- درگاه مدیریت فقط نقش را بررسی می‌کند. تا زمانی که APIهای واقعی مدیریت بررسی نشده‌اند، عملیات مدیریتی ساختگی یا تغییردهندهٔ داده ارائه نمی‌شود.
- گردش‌کار GitHub اکنون نحو Bash، HTML، بلوک‌های JavaScript، وجود مسیرهای ضروری و وضعیت مسیرهای زنده را بررسی می‌کند و یک بستهٔ خروجی قابل دریافت به‌عنوان Artifact می‌سازد.

## محدودیت‌های مهم استقرار

آرشیو ورودی `ghestine-all3.zip` عمداً حفظ شده و دست‌نخورده است؛ فایل‌های اصلاح‌شده در پوشهٔ `source/all3/` قرار دارند و خروجی انتشار جدید در Artifact گردش‌کار ساخته می‌شود. این دو را نباید با یکدیگر اشتباه گرفت.

بررسی قبلی دامنه نشان داده بود که صفحهٔ اصلی زنده هنوز عنوان قدیمی «قسطینه | خرید اقساطی» دارد، مسیرهای `/login.html`، `/register.html`، `/profile.html` و `/admin.html` پاسخ 404 می‌دادند، و `/api/v1/loan-products` پاسخ 200 می‌داد. این وضعیت باید دوباره در هر اجرای CI بررسی شود.

آخرین آزمون تولید در ۲۰۲۶-۱۰-۲۶ نشان داد `GET /api/v1/security/captcha` و مسیرهای OTP پاسخ `404` می‌دهند؛ مسیرهای موجود `POST /api/v1/Auth/login` و `POST /api/v1/Auth/register` به درخواست‌های آزمایشی نامعتبر `400` دادند، اما قرارداد DTO آن‌ها از سورس در دسترس قابل تأیید نیست. `GET /api/v1/Auth/me` پاسخ `401` می‌دهد. صفحهٔ اصلی فعلی هنوز عنوان «قسطینه | خرید اقساطی» دارد و صفحات ورود، ثبت‌نام، حساب و مدیریت روی سایت 404 هستند.

بررسی استقرار نشان داد Secrets لازم GitHub Actions با نام‌های `DIGIBAIL_SSH_PRIVATE_KEY`، `DIGIBAIL_SSH_KNOWN_HOSTS`، `DIGIBAIL_SSH_HOST` و `DIGIBAIL_SSH_USER` در محیط اجرای فعلی تنظیم نشده‌اند. بنابراین این محیط امکان ورود SSH به سرور و اعمال تغییرات را ندارد؛ هیچ تغییری روی سایت زنده انجام نشده است. گردش‌کار استقرار اکنون فقط با اجرای دستی و تأیید صریح قابل شروع است.

این بسته فایل پروژهٔ کامل .NET با `.sln` و `.csproj` ندارد؛ بنابراین تکمیل سورس وب به معنی build یا تأیید بک‌اند نیست. نصب‌کنندهٔ امنیت اکنون پیش‌بررسی ساختار پروژه را پیش از هر تغییر انجام می‌دهد و اگر پروژه با ساختار `Ghestine.API` سازگار نباشد، بدون تغییر فایل‌ها متوقف می‌شود. این نصب‌کننده را روی `public_html` یا کانتینر کامپایل‌شدهٔ `LoanSystemAvizhe.Site.dll` اجرا نکنید. گردش‌کار استقرار اکنون قبل از دست زدن به فایل‌های تولیدی، وجود APIهای کپچا و امنیت را می‌سنجد؛ اگر APIهای `/api/v1/security/*` هنوز روی سرور نصب نشده باشند، انتشار را متوقف می‌کند و فایل‌های زنده را تغییر نمی‌دهد. برای انتشار کامل باید ماژول امنیت در پروژهٔ واقعی .NET ادغام و build شود، نصب‌کننده پس از بررسی و بکاپ اجرا شود و سپس استقرار استاتیک از طریق SSH انجام گیرد. این تغییرات به‌خودی‌خود سایت زنده را تغییر نمی‌دهند.

هیچ رمز، کلید پیامک، توکن یا اطلاعات شخصی واقعی نباید در GitHub قرار داده شود.
