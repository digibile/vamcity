# مهاجرت دیتابیس VamCity از SQL Server به MariaDB

**وضعیت: آماده‌سازی و مستندسازی؛ انتقال واقعی هنوز اجرا نشده است.**

## مقصد قطعی

- دیتابیس مبدأ مورد درخواست: `vamcitydigibilepay` روی SQL Server ویندوز
- دیتابیس مقصد: `vamcitydigibilepay` روی MariaDB 10.6 لینوکس
- مقصد، یک دیتابیس واحد است. این سند ایجاد سه دیتابیس مقصد جداگانه را تأیید نمی‌کند.
- نسخه SQL Server باید تا پایان تطبیق و تأیید نهایی بدون تغییر و قابل بازیابی باقی بماند.

## آنچه از بررسی بکاپ‌ها ثبت شده است

در محیط ایزوله، سه بکاپ SQL Server با نام‌های بازیابی‌شده زیر بررسی شده‌اند:

| نام بازیابی‌شده | جدول | رکورد |
|---|---:|---:|
| `vamcityc_vamcity_import_20261028` | 88 | 531,172 |
| `vamcityc_bluvamdb` | 56 | 286,597 |
| `vamcityc_transferDb` | 12 | 29 |
| **جمع** | **156** | **817,798** |

برای دیتابیس اصلی بررسی‌شده، inventory شامل 957 ستون، 100 ستون کلید در 88 قید PK/Unique، تعداد 188 نام قید FK و 297 ردیف ستون ایندکس در 283 نام ایندکس است. در آن نسخه از بکاپ، View، Stored Procedure، Function و Trigger گزارش نشده است.

**نکته نام‌گذاری:** `vamcityc_vamcity_import_20261028` نام دیتابیس restore شده برای تحلیل است. هنوز باید با metadata خود فایل بکاپ/SQL Server تأیید شود که محتوای آن دقیقاً همان دیتابیس اصلی `vamcitydigibilepay` است. این تفاوت نام به‌تنهایی اثبات نمی‌کند که دو دیتابیس متفاوت‌اند.

## شواهد و محدودیت‌های فنی

1. یک اسکریپت قدیمی با نام `scripts/import-vamcity-real-data.mjs` وجود دارد که مقصد آن PostgreSQL و جدول خام آن `legacy_source_data` است. اجرای ثبت‌شده آن، انتقال نهایی به MariaDB محسوب نمی‌شود.
2. مستند قبلی `VAMCITY-MYSQL-MIGRATION-FA.md` از schema آزمایشی MariaDB و اجرای موفق dry-run ابزار PHP خبر می‌دهد؛ اما طبق همان مستند، هیچ رکوردی در مقصد MariaDB وارد نشده است.
3. طرح قدیمی سه دیتابیس مقصد پیشنهاد می‌کرد. این طرح با تصمیم فعلی «یک دیتابیس مقصد به نام `vamcitydigibilepay`» منطبق نیست و نباید بدون بازطراحی mapping اجرا شود.
4. در تلاش قبلی اتصال به MariaDB، اعتبارنامه `da_admin` با خطای 1045 رد شده است. فایل تنظیمات DirectAdmin نباید کورکورانه بازنویسی شود و اسکریپت reset رمز نیز بدون بررسی و مجوز اجرا نشود.
5. در آخرین خروجی دیسک ثبت‌شده، فضای آزاد حدود 2.1GB و مصرف 98٪ بوده است. این عدد وضعیت همان زمان است، نه اندازه‌گیری زنده. پیش از import باید فضای آزاد فعلی و اندازه dump/temporary files دوباره سنجیده شود.
6. collation مبدأ SQL Server یعنی `SQL_Latin1_General_CP1_CI_AS` با collation مقصد پیشنهادی `utf8mb4_unicode_ci` یکسان نیست؛ رفتار مقایسه رشته‌ها و unique indexها باید در mapping بررسی شود.

## مراحل الزامی پیش از اجرای import

- [ ] تأیید هویت بکاپ اصلی در برابر دیتابیس ویندوزی `vamcitydigibilepay`
- [ ] تهیه و اعتبارسنجی بکاپ مستقل از مقصد MariaDB
- [ ] تأیید فضای آزاد کافی برای staging، لاگ و عملیات rollback
- [ ] دسترسی معتبر و محدودشده برای حساب مهاجرت MariaDB؛ بدون قراردادن رمز در Git
- [ ] تهیه mapping قطعی نوع داده‌ها، NULL، تاریخ/زمان، decimal، bit، identity و مقادیر پیش‌فرض
- [ ] تعیین ترتیب import بر اساس FK و مدیریت چرخه‌های وابستگی
- [ ] حفظ شناسه‌های اصلی و بازتنظیم AUTO_INCREMENT پس از import
- [ ] رسیدگی به برخورد نام جدول‌ها در صورت ادغام داده‌های جانبی؛ هیچ جدول یا رکوردی نباید بی‌صدا حذف یا overwrite شود
- [ ] اجرای آزمایشی روی clone و گزارش تفاوت تعداد رکوردها
- [ ] اجرای نهایی در پنجره نگهداری، سپس تطبیق تعداد رکورد هر جدول، کلیدها، روابط و نمونه‌برداری داده
- [ ] نگهداری SQL Server مبدأ تا تأیید کتبی نتیجه
